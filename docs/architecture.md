# Архитектура EMI

## Общая схема

EMI построена по модульному принципу. Ядро (`EMI`) содержит всю логику RPC, управления соединениями, пулинга памяти и middleware. Транспортные модули подключаются через интерфейсы и не зависят друг от друга.

```
EMI (ядро)
├── RPC                 Регистрация, диспетчеризация, сериализация вызовов
├── Indicators          Типизированные дескрипторы удалённых методов
├── Network             Транспортные интерфейсы и middleware-конвейер
├── NGC                 Пул массивов байт
├── Headless            RPC без встроенного транспорта
├── DebugLog            Логирование (только DEBUG-сборка)
└── Exception           Собственные исключения

EMI.NetTCPV3            TCP-транспорт
EMI.NetUDP              UDP-транспорт с надёжной доставкой
EMI.SyncInterface       IL-emit генерация RPC из интерфейсов
EMI.NetStream           Удалённый доступ к Stream и загрузка файлов
EMI.DebugServer         Мост между рабочим сервером и отладчиком
EMI.Debugger            WPF-приложение для диагностики
```

Зависимости направлены от периферии к ядру: все модули ссылаются на `EMI`, но `EMI` не знает о конкретных транспортах. Внешняя зависимость: `SmartPackager` для бинарной сериализации.

## Транспортная абстракция

Три интерфейса определяют контракт транспорта:

`INetworkService` : фабрика, создаёт экземпляры клиента и сервера. Передаётся в конструктор `Server` или `Client`.

`INetworkServer` : принимает входящие соединения, возвращает `INetworkClient` для каждого подключённого клиента.

`INetworkClient` : отправляет и получает массивы байт. Содержит свойства состояния: `IsConnect`, `RemoteAddress`, метрики скорости.

Чтобы добавить новый транспорт, достаточно реализовать эти три интерфейса. Всё остальное (RPC, middleware, пинг) работает автоматически.

## TCP-транспорт (NetTCPV3)

Построен на `System.Net.Sockets.TcpClient`. Крупные сообщения автоматически разбиваются на сегменты по 1023 байта с заголовком `MessageSegmentHeader`. Заголовки пакетов работают через `unsafe`-указатели на предвыделенные буферы для минимизации аллокаций.

Формат адреса: `IP#Port`, например `127.0.0.1#9000`.

Настройки: `NoDelay = true`, `SendTimeout = 60s`.

## UDP-транспорт (NetUDP)

Собственный протокол надёжной доставки поверх сырого UDP:

Надёжная доставка: порядковые номера, битовое поле подтверждений (окно 32 пакета), ретрансмиссия с экспоненциальным backoff (100ms до 1000ms, максимум 15 попыток).

Фрагментация: сообщения крупнее MTU (1200 байт) автоматически разбиваются и собираются на принимающей стороне. Таймаут сборки: 10 секунд.

Рукопожатие: `ConnectionRequest` / `ConnectionAccept` с проверкой токена.

Heartbeat: ping/pong каждую секунду. Тишина 10 секунд означает разрыв соединения.

Ненадёжная доставка: отдельный тип пакетов для данных, которые можно терять (позиции, состояния).

## Middleware-конвейер

Пакеты проходят через цепочку обработчиков `IPacketMiddleware`:

При отправке : данные последовательно обрабатываются каждым middleware (сжатие, затем шифрование).

При получении : обратный порядок (расшифровка, затем распаковка).

Встроенные middleware:

`LZ4Middleware` : сжатие через LZ4. Уменьшает объём трафика без заметных задержек.

`AesGcmMiddleware` : AES-256-GCM шифрование. Сессионный ключ согласуется во время handshake через стратегию `IKeyExchange` и **никогда не передаётся открытым текстом**. Каждый middleware имеет `Id` и `Version` для проверки совместимости во время рукопожатия.

Обмен ключами — сменяемая стратегия (`IKeyExchange`), образующая лестницу уровней безопасности: PSK (ключ роздан вне сети), RSA key-transport (клиент шлёт AES-ключ под публичным ключом сервера), RSA с пиннингом (защита от активного MITM). По умолчанию при `UseEncryption=true` — RSA. Подробнее: [docs/security.md](security.md). Ключ уникален на каждое соединение.

Активируются через свойства `UseEncryption` и `UseCompression` до вызова `Start()` / `Connect()`.

## RPC-движок

Центральная часть библиотеки. При регистрации метода его строковое имя хешируется детерминистически (DJB2-вариант через `Deterministic.DeterministicGetHashCode()`), и по этому хешу происходит диспетчеризация.

Две области видимости RPC:

`Server.RPC` : глобальный реестр. Методы доступны всем подключённым клиентам.

`Client.LocalRPC` : реестр конкретного клиента. Методы доступны только этому соединению.

При получении пакета сначала проверяется глобальный реестр, затем локальный.

Структура пакета: байт типа (`PacketType`), 4 байта ID метода, остаток: сериализованные параметры через `SmartPackager`.

Если зарегистрированный метод выбрасывает исключение, оно перехватывается и логируется. Вызывающая сторона получает значение по умолчанию. Это предотвращает падение всего сервера из-за одного сбойного обработчика.

## NGC (пул массивов)

`NGCArray` реализует пул байтовых массивов. При создании ищется подходящий массив в пуле (от точного размера до 10x). При освобождении массив возвращается в пул с меткой времени. Фоновая задача `Cleaner()` удаляет просроченные массивы (время жизни: 1 минута).

`EasyArray` : простая обёртка над обычным `byte[]` без пулинга, для мелких или долгоживущих массивов.

В DEBUG-сборке доступны счётчики: количество использованных и свободных массивов, суммарный объём памяти.

## SyncInterface

IL-emit компилятор, генерирующий RPC-прокси из обычного C#-интерфейса. Для каждого интерфейса создаются два класса: один для вызывающей стороны (формирует RPC-вызов), другой для принимающей (регистрирует реализацию).

Поддерживаемые сигнатуры: `void`, методы с возвращаемым значением, `async Task`, `async Task<T>`.

Если последний параметр метода — `CancellationToken`, он автоматически пробрасывается в `RCall` для отмены RPC-вызова (отправки или ожидания ответа). На принимающей стороне обработчик получает `default(CancellationToken)`. Параметр `CancellationToken` не сериализуется и не передаётся по сети.

## Headless

`HeadlessHandler` предназначен для ситуаций, где транспорт реализован внешним средством (например, Steam P2P). Библиотека не управляет отправкой и получением: пользователь предоставляет делегат `SendPacket` и вызывает `AcceptPacket()` вручную. Вся RPC-система и middleware при этом работают как обычно. Перенаправление (`RPC_Forwarding`) не поддерживается.

## Отладчик

WPF-приложение, подключающееся к `EDebuggerServer`. Показывает:

Состояние сервера (запущен/остановлен, адрес, количество клиентов).

Список клиентов с информацией о каждом (адрес, пинг, скорость, состояние).

Зарегистрированные RPC-методы с именами и типами.

Состояние пула NGC (занятые и свободные массивы, память).

Поток логов в реальном времени.

Для работы отладчика `EMI` должна быть скомпилирована в конфигурации DEBUG, поскольку события логирования, доступ к списку клиентов и имена RPC-методов доступны только в отладочной сборке.

## Обработка ошибок

Библиотека определяет собственные исключения:

`AlreadyException` : повторное действие (запуск уже запущенного сервера, подключение уже подключённого клиента).

`ClientDisconnectException` : клиент отключился во время длительной операции.

`ClientViolationRightsException` : клиент выполнил запрещённое действие (приводит к разрыву соединения).

`RegisterLimitException` : превышен лимит зарегистрированных RPC-функций (2^16).

`RPCRegisterNameException` : дублирование имени RPC-метода.

`InvalidInterfaceException` (SyncInterface) : переданный тип не является интерфейсом или содержит свойства.
